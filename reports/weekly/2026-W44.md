## Adversarial Triad: HorizonStream —— 「48 幀訓練跑 1 萬幀」是否拔掉了 feed-forward 3R 的記憶體死刑？

**背景**：HorizonStream（2605.23889, cs.CV）把 streaming 3D reconstruction 的幾何傳播形式化為 *evidence influence kernel*，用**可學習 channel-wise decay 的幾何線性注意力**分解長時序、用**spatiotemporal RoPE 局部注意力**抑制 attention sink，讓**僅 48-frame 訓練**的模型在 **>10,000 frames** 上 constant-memory / linear-time 穩定重建，並宣稱解掉滑窗與因果注意力在長序列的 drift、jitter、cache 飽和。它直接撞上 §13.1 反對欄裡的兩條硬證據：**FastVGGT 的 quadratic memory（arXiv 2509.02560）** 與 **arXiv 2512.21691 的「global self-attention 隨長度坍縮成 rank-1」**。（日報未報告其 ATE/drift 數值與所用 benchmark。）

**🔴 Bull（這是真信號，把 §13.1 的記憶體反對打回去）**

1. **機制對症下藥，不是刷點**：linear attention 把全序列注意力 O(N²) 換成可分解的 kernel，局部 RoPE 注意力專打 attention sink——這正是 2512.21691 描述 rank-1 坍縮與 FastVGGT 描述 quadratic blowup 的**同一機制病理**。作者不是繞過問題，是**指著病竈下藥**。
2. **200× 外推的實證**：48-frame 訓練 → >10,000 frames 仍穩定，這是 200 倍以上的長度外推（非內插）。若「幾百幀就爆」是根本限制，這種外推不可能維持 constant memory——這條數字本身就是對「quadratic 是命定」的反例。
3. **同時打品質不只是記憶體**：宣稱解決 drift、jitter、cache 飽和，意味它不是「省記憶但犧牲一致性」的典範。若成立，滑窗 streaming 的長序列退化（§13.3 說 feed-forward 在長時程 SLAM 尚不能取代 backend 的關鍵理由之一）被削掉一角。
4. **移動 time 軸**：把 filter-streaming 從「數百幀可行」推到「萬幀可行」，這是 feed-forward 3R 從 offline/few-view 走向長時程 streaming 的**前置條件**——沒有它，§13.3「feed-forward 取代 per-scene」永遠只能在短序列說。

**🔵 Bear（過早慶祝；這篇沒有動到 §13.1 的立場）**

1. **它不是 VGGT——它承認了坍縮**：HorizonStream 用幾何線性注意力 + 局部注意力**取代**了 global self-attention。2512.21691 說的是「VGGT 的 *global self-attention* 坍縮」——這篇**在架構上移除了那個機制**，等於默認 global attention 會爆，而非反駁。所以 §13.1「VGGT 是 shift」的爭議**一寸未動**，反而佐證「純 VGGT 走不通、要改架構」。
2. **mono + reconstruction ≠ SLAM**：日報標籤是 `sensor: mono`、`problem: reconstruction`，**沒有 IMU、沒有 loop closure**。§13.3 明寫 feed-forward **沒有取代** real-time SLAM with IMU + loop closure。streaming reconstruction 的記憶體突破，對「VSLAM 後端仍屬 VIO/VINS」這條立場**零衝擊**。
3. **「constant memory」≠「constant accuracy」**：日報**未報告** ATE/drift。長序列 streaming 的經典失敗正是「記憶體守恆但全局一致性漂移」。在拿到 >10,000 幀的 drift 曲線前，只能說記憶體解了，品質未證。
4. **Wu 2025 的那些反對，這篇一個都沒碰**：518px 輸入上限、建築周邊破洞、俯視高結構失敗——這些是**精度/覆蓋**問題，不是記憶體。Bull 第 3 點把「drift/jitter」賣成勝利，但 §13.1 真正致命的 Wu 2025 證據全在精度側，未受挑戰。
5. **48 幀訓練的外推風險**：decay 機制會**過度平滑**以換取長時穩定，動態場景（移動物體）最可能被 decay 抹掉——日報未報告動態場景結果，這是典型「靜態 benchmark 好看、動態崩」的已知模式。

**🟢 Arbiter（裁決）**

1. **§13.1 立場更新：微調，非重寫、非維持不動。** 「VGGT 是重要範式信號但不是 shift」**維持**；但反對欄裡「quadratic memory 是根本缺陷（FastVGGT）」這條**必須降級為「vanilla global attention 的缺陷，linear-attention 變體可解」**。方向：把爭議從「VGGT 能不能用」推向「哪種 feed-forward 架構能用」——這恰好是 **3R-SLAM Hybrid 精神**的又一次驗證（backbone 需架構改造 + 傳統後端）。**移動幅度：微調（措辭級），不是立場級。**

2. **軸移動：time 軸 +（feed-forward 長時程 streaming 可行性↑），paradigm 軸不動。** 這是**工程使能**而非範式轉移——它讓 feed-forward 3R 的「長序列」子能力變真，但沒讓「feed-forward 取代 per-scene」在 SLAM/imposed-backend 場景成立。

3. **關鍵代理指標 + kill condition（我設的判準）**：
   - **確認需看到**：(a) 在 >5,000–10,000 幀長序列上，**head-to-head vs 固定滑窗/因果注意力基線，報 ATE/drift 而非只報記憶體**；(b) 在含移動物體的動態序列上，decay 不至於把目標抹掉（不是只跑靜態室內）；(c) 把該 linear-attention 骨幹**接進有 IMU + loop closure 的 SLAM 迴路**而不破後端。
   - **Kill condition**：若 >10,000 幀時 ATE **超線性成長**（相對固定窗基線），或動態場景因 decay 過平滑而漏移動物，「constant memory 且品質不降」的宣稱即死；若後續把此機制接進 SLAM 卻仍需原封不動的外掛後端才能收斂，「feed-forward 取代 backend」的推進亦告吹。

4. **用戶行動建議**：
   - **盯「HorizonStream-style linear attention 有沒有被搬進 VGGT 家族骨幹」**——這才是 §13.1 的真測試；單純另一篇 streaming 3R 不算。
   - **對「constant memory」一律先問 drift 數字**：在看到 >10k 幀 head-to-head ATE 前，把它當「記憶體解了、品質待證」。
   - **別把這讀成「feed-forward SLAM 到來」**：mono reconstruction 的記憶體突破，與 §13.3 的「IMU+loop closure 仍需傳統後端」是兩件事，實務選型別被行銷詞牽著走。
